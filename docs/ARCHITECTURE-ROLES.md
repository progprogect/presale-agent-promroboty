# Роли, назначения и очередь событий (архитектура)

Цель: делегировать подготовку и проверку КП. Админ (Микита) заводит людей по email,
назначает их на проекты с ролью и набором разделов; каждый работает из личного кабинета;
локальная агентская система узнаёт обо всех изменениях на портале через очередь событий
и доводит процесс (почта, сборка документов) у себя — ключи и переписка не покидают локальную машину.

## Принятые решения

1. **Вход без паролей**: у каждого человека персональная ссылка-токен `/u/<token>`
   (как стиль портала — работаем по ссылкам). Email — адрес доставки приглашений и уведомлений,
   не логин. Пароль есть только у админки (HTTP Basic, env `ADMIN_USER`/`ADMIN_PASSWORD`).
2. **Почта — только с локальной машины.** Сервер никому не пишет: он кладёт событие в очередь
   (`events`), локальный слушатель `tools/portal_events.py` забирает и готовит письмо
   (первые шаблоны — на утверждение, дальше — по постоянному разрешению).
3. **Не webhook и не частый polling, а long-poll**: слушатель держит запрос
   `GET /api/agent/events?after=<id>&wait=25` — сервер отвечает сразу, как появилось событие
   (задержка ~0, трафик копеечный). **Автовосстановление**: номер последнего обработанного
   события хранится локально (`leads/_portal-reviews/agent_state.json`); после сбоя/отключения
   слушатель при старте забирает всё пропущенное (`after=<последний>`). Очередь — append-only
   в Postgres, ничего не теряется. Слушатель пингует сервер; админка показывает
   «агент онлайн/оффлайн» и число необработанных событий, кнопка «Проверить задачи»
   кладёт событие `check` (агент отвечает на него — живость видна).
4. **Роли** (ключ → за что согласует; названия правятся в одном месте, `ROLES` в main.py):
   - `delivery` — delivery-менеджер: всё по проекту, гейты, финальное «пакет принят»;
   - `tech` — технолог: компоновка ячейки целиком и всё вокруг неё;
   - `electro` — электрика и электросеть;
   - `robo` — подрядчик по роботам: КД и установка робота (без сопутствующего и ПО);
   - `soft` — специалист по ПО;
   - `viewer` — только смотреть.
5. **Назначение** = человек × проект × роль × разделы (вкладки карточки) × доступ к ТКП
   (отдельный флаг `kp`). Личный кабинет показывает только назначенное; имя валидатора
   в карточках подставляется из токена (`?u=<token>`).
6. **Разделение сред**: публичный репозиторий не содержит ни людей, ни событий — всё в Postgres.

## Схема данных (Postgres)

- `people(id, name, email, org, role, token, active, created)`
- `assignments(id, person_id, slug, role, pages jsonb, kp bool, created)` — pages: список вкладок, null = все кроме ТКП
- `events(id, ts, type, slug, payload jsonb, done, done_ts)` — outbox для локального агента
- `kv(key, value jsonb)` — служебное (последний пинг агента)
- `reviews` — как было (слои правок валидаторов)

События: `assign` (назначение → письмо-приглашение), `review_done` (валидатор завершил проверку
раздела), `check` (ручная проверка живости/задач с админки), `note` (произвольное поручение агенту).

## Конвейер (куда движемся, фазы)

Процесс: ТЗ → **вопросы и решения** (гейт: delivery жмёт «согласовано, двигаемся») →
пакет: схема+процесс+решение+WBS+BOM (**RFQ поставщикам — батчем**: короткие точечные вопросы,
только блокирующее, не чаще раза на этап; пока ответа нет — позиция живёт с «оценкой» и источником)
→ **мультисогласование по ролям** (каждый аппрувит свои разделы, delivery — финальный) →
сборка КП → согласование КП (видят только с флагом `kp`) → отправка заказчику (после «да» Микиты).

- **Фаза 1 (этот коммит)**: люди, роли, назначения, персональные кабинеты, админ-дашборд
  (пайплайн × разделы × люди, статус агента), очередь событий + локальный слушатель с догоном,
  событие `review_done` из карточек, черновики приглашений.
- **Фаза 2**: вкладка «Вопросы и решения» с гейтом delivery; матрица аппрувов по ролям на
  «Обзоре» (кнопка «согласовано» на роль × раздел), жёсткое закрытие карточек по токену
  (`restricted: true` у сделки), авто-отправка приглашений после утверждения шаблона.
- **Фаза 3**: вкладка ТКП по флагу `kp`, RFQ-батчер (агрегация открытых вопросов по поставщику
  в одно короткое письмо), пост-КП поток (документы заказчику).
